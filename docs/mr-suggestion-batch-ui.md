# Selecting and applying multiple code suggestions

An MR discussion page offers **Apply multiple suggestions** when at least two loaded suggestions are eligible and have unique global identities. The selection screen starts empty. Select at least two targets, inspect their previews, and choose **Review selected**. The confirmation shows every selected original/replacement patch, range, and server state before **Apply selected**. Opening, selecting, navigating back, or cancelling sends no write. An optional commit message retains its exact whitespace; an empty field uses GitLab's default. The existing project/IID discussion route owns this flow.

Selection uses loaded discussions only, without eager pagination or selecting hidden pages. Unknown, applied, system, non-text, malformed, and ambiguous suggestions are unavailable. Patch applicability does not imply permission: GitLab decides authorization. The controller snapshots the selected set and holds the shared comment/reply/resolution/application reservation. Pending pagination also blocks batch application and recovery.

Before the single batch write, every selected discussion is fetched once through the authenticated single-discussion endpoint. Each selected note identity, position, patch content, inclusive range and flags must still match the review. A failed read, changed patch or ambiguous identity prevents the entire dispatch. There is no single-write fallback or automatic subset application. The real repository forwards the selection to the [batch API](mr-suggestion-batch-api.md), preserving the optional message. Only complete, unique, matching `applied=true` confirmation succeeds; returned known patch metadata must agree. Sparse and reordered confirmation is supported. Success refreshes discussions, MR detail and the authoritative review snapshot in the originating session, without comment analytics.

Failure or unconfirmed completion retains the message and requires explicit **Reload selected discussions**. Recovery reads every selected discussion before replacing any loaded cache entry, preserving pagination. A failed intermediate read leaves the cache unchanged and keeps confirmation and selection changes disabled. A complete read displays changed patches for renewed confirmation. Missing or ambiguous suggestions lose their old code preview and remain explicitly selected but unavailable until the user returns to selection and deselects them. Already applied, unknown or inapplicable targets block another application. Recovery itself never writes or infers success for a subset.

Pending reads/writes disable input, cancellation, back navigation and duplicate confirmation. Account or MR replacement hides the old source and cancels undispatched follow-up reads and writes. Late errors, success feedback and refreshes cannot affect the replacement view. A request already accepted by GitLab cannot be undone by view replacement. These are returned-state checks, not a branch SHA guard, rollback or a client guarantee that a server batch is atomic. Closing and reopening starts a new flow; it does not persist an uncertain-operation journal.

All five locales use the same responsive dialog. Short windows with keyboard insets scroll the actions together with the content, including at doubled text size. Existing single suggestion application, comment drafts and original-diff context remain available.

## Verification and synthetic captures

Tests were written before the controller methods and batch entry action, and failed for those missing behaviors. A compact keyboard/large-text test then reproduced an action overflow before its layout fix. Controller/widget coverage includes exact selected subsets and drafts, all preflights before one batch, same-thread read deduplication, changed and duplicate patches, sparse/reordered or incomplete confirmation, reservations and pagination, account/view cancellation, success-only refreshes, complete staged read-only recovery and explicit missing-target presentation. Real repository tests cover subpath/PAT routing, null/empty/exact messages, returned server order and write replay protections.

Layout tests cover five locales at 390, 800 and 1200 logical pixels in both themes and a 320 × 600 window with keyboard insets and doubled text. These captures use dummy fixtures and SDK fonts in Flutter widget tests. No live GitLab write, physical-device or store validation is claimed. Regenerate with `LABFOX_BATCH_UI_CAPTURE=<absolute-output-directory>` and `FLUTTER_ROOT=<Flutter-SDK-directory>`, running `mr_suggestion_batch_application_test.dart` with the name filter `synthetic batch confirmation capture`. Mobile content scrolls to reveal the remaining patch and commit message.
